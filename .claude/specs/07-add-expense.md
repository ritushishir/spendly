# Spec: Add Expense

## Overview
Step 7 is the first step where a Spendly user can put their own data into the
app. Everything up to now has been read-only: registration and login create an
account, and `/profile` displays the eight rows `seed_db()` inserted. There is
no way to record a real expense — `/expenses/add` is still a placeholder route
returning a plain string. This step turns it into a real `GET|POST` route with a
form: amount, category, date, and an optional description. A successful submit
inserts one row scoped to `session["user_id"]` and redirects to `/profile`,
where the new expense immediately appears in the transaction list and rolls into
the summary stats and the category breakdown. It also introduces the app's first
write path for user-supplied data, so the validation shape it establishes —
server-side checks, errors re-rendered into the same form with the user's input
preserved — is what Step 8 (edit) and Step 9 (delete) will follow.

## Depends on
- Step 1: Database setup — `get_db()`, the `expenses` table, `CATEGORIES`
- Step 2: Registration — accounts exist, and the "re-render the form with an
  `error` string" pattern this step copies
- Step 3: Login / Logout — `session["user_id"]` and the `@login_required`
  decorator
- Step 4: Profile page UI — the page the new expense shows up on
- Step 5: Backend connection — `/profile` reads live rows via
  `get_expenses_for_user()` / `get_category_totals_for_user()`
- Step 6: Date filter — `_parse_date_arg()` in `app.py`, reused here to
  validate the submitted date

## Routes
- `GET /expenses/add` — render an empty expense form, date pre-filled with
  today. Access: logged-in only (`@login_required`).
- `POST /expenses/add` — validate the submitted fields, insert one expense for
  the signed-in user, redirect to `url_for("profile")`. On a validation failure,
  re-render the form with an `error` string and the submitted values still
  filled in. Access: logged-in only (`@login_required`).

This **replaces** the existing placeholder at `app.py:300` — the route path and
the `add_expense` function name stay the same, so nothing else has to be
rewired. Note the placeholder currently has no `methods=` argument and no
`@login_required`; both must be added.

## Database changes
No database changes. The `expenses` table already has everything this step
writes: `user_id INTEGER NOT NULL REFERENCES users(id)`, `amount REAL NOT NULL`,
`category TEXT NOT NULL`, `date TEXT NOT NULL`, `description TEXT` (nullable —
`seed_db()` already inserts a `None` description for the "Other" row), and
`created_at` with a `datetime('now')` default. No new tables, columns, indexes,
or constraints.

## Templates
- **Create:** `templates/add_expense.html`
  - Extends `base.html`; `{% block title %}Add expense — Spendly{% endblock %}`.
  - A single `<form method="POST" action="{{ url_for('add_expense') }}">` in a
    centred card, laid out with the existing `.form-group` / `.form-input` /
    `.btn-submit` classes rather than new ones.
  - Fields, in this order:
    - **Amount** — `<input type="number" name="amount" step="0.01" min="0.01"
      required autofocus>`, prefixed with a ₹ symbol in the label or an adornment
      span.
    - **Category** — `<select name="category" required>` whose `<option>`s are
      generated by looping over the `categories` value passed in from the route
      (which is `CATEGORIES` imported from `database.db`). Never hardcode the
      seven strings in the template.
    - **Date** — `<input type="date" name="date" required>`, pre-filled with
      `form.date` (today on a fresh GET).
    - **Description** — `<input type="text" name="description">`, explicitly
      labelled optional.
  - Renders `{% if error %}` into a `.auth-error`-style block above the form —
    the same plain-string pattern as `login.html` / `register.html`, not flash
    messages.
  - Every field re-populates from a `form` dict so a rejected submit never makes
    the user retype what they already entered, including the chosen category
    (`{% if cat == form.category %}selected{% endif %}`).
  - A "Cancel" link back to `url_for('profile')` next to the submit button.
- **Modify:** `templates/profile.html`
  - Add an "Add expense" call-to-action linking to `url_for('add_expense')`.
    Put it in the `.profile-head` block, right-aligned against the
    "Your profile" heading, using `.btn-primary`.
  - Update the two "No expenses yet" empty states so they point at the new
    route — an account with nothing recorded should be one click from adding
    something. The "no expenses in this range" copy from Step 6 stays as it is.

## Files to change
- `database/db.py`
  - Add `create_expense(user_id, amount, category, date, description=None)` to
    the Expenses section, below `get_category_totals_for_user()`. Inserts one row
    with a parameterised `INSERT` and returns `cursor.lastrowid`. Same
    `try/finally` + `conn.close()` shape as `create_user()`; the caller owns
    validation, this helper owns the SQL.
  - It stores what it is given — no clamping, rounding, or category checking in
    the data layer. Validation belongs in the route so the error can be shown to
    the user.
- `app.py`
  - Import `create_expense` and `CATEGORIES` from `database.db` (add to the
    existing alphabetical import block).
  - Add `_parse_amount(value)` next to the other module-level helpers: strips the
    input, rejects blank, rejects anything `float()` can't parse, rejects `<= 0`
    and non-finite values, rejects anything above a sane ceiling (`1_000_000`),
    and returns the value rounded to 2 decimals. Raises `ValueError` with a
    message the route can show.
  - Replace the `add_expense()` placeholder with the real `GET|POST` view,
    decorated `@login_required`. On GET, render the form with
    `form={"amount": "", "category": "", "date": <today ISO>, "description": ""}`
    and `categories=CATEGORIES`. On POST: read the four fields, validate in the
    order amount → category → date, and on the first failure re-render with
    `error` set and the submitted `form` values preserved. On success call
    `create_expense(session["user_id"], …)` and `redirect(url_for("profile"))`.
  - Reuse `_parse_date_arg()` from Step 6 for the date rather than writing a
    second date validator, but treat a missing date as an error here (it is a
    required field, not an open-ended filter bound).
- `static/css/style.css`
  - Add the form-page wrapper classes the new template needs — an
    `.expense-form-section` / `.expense-form-card` pair sized off `--auth-width`,
    a `.form-select` rule that matches `.form-input` (native `<select>` ignores
    some of it, so set `appearance`, padding, and the same border/background
    tokens), a `.form-hint` for the "optional" note, and a `.form-actions` row
    that puts `.btn-submit` and a `.btn-ghost` Cancel link side by side.
  - Add a `.profile-head` modifier so the heading and the new CTA sit on one row
    and stack on narrow screens.
  - Tokens only — `--paper-card`, `--border`, `--radius-md`, `--ink-muted`,
    `--accent`, `--font-body`, etc.

## New dependencies
No new dependencies. `date`/`datetime` are stdlib and already imported in

## Rules for implementation
- No SQLAlchemy or ORMs — raw `sqlite3` through `get_db()` only.
- Parameterised queries only. Every one of the four submitted fields is
  untrusted user input and travels as a bound parameter; nothing is interpolated
  into the `INSERT`.
- Passwords hashed with werkzeug — unchanged; this step touches no auth code.
- Use CSS variables — never hardcode hex values.
- All templates extend `base.html`.
- **`user_id` comes from `session["user_id"]`, never from the form.** There must
  be no hidden `user_id` input and no way for a request to name the account it
  writes to. This is the same ownership rule that protects the read queries.
- The route must go through `database/db.py` — no `sqlite3.connect()` in
  `app.py`.
- **Category is validated against `CATEGORIES` server-side.** The `<select>` is a
  convenience, not a constraint: a hand-crafted POST with
  `category=Cryptocurrency` must be rejected with an error, not inserted.
- Amount is stored as a positive `REAL` rounded to 2 decimals. Reject `0`,
  negatives, `abc`, `NaN`, `Infinity`, and an empty field — each with a message
  naming what is wrong. A bad amount must never 500.
- Date is stored as zero-padded ISO `YYYY-MM-DD` and nothing else. Step 6's
  filtering depends on that format being uniform — a row stored as `4/8/2026`
  would silently drop out of every range query.
- **Future dates are rejected** ("You can't record an expense dated in the
  future"). This is a deliberate product call: Spendly records money already
  spent, and `seed_db()`'s `day()` helper already never writes past today. Say so
  if you'd rather allow them — it is one condition to drop.
- A blank description is stored as SQL `NULL`, not `""`, so it matches the
  seeded row and `profile.html`'s `{{ txn.description or "—" }}` renders the
  dash. Strip it first; whitespace-only is blank.
- Validation errors re-render the form with HTTP 200 and the user's values
  intact — no redirect-and-lose-the-input, no flash messages, no traceback.
- Success redirects to `/profile` rather than re-rendering, so a refresh can't
  double-post the same expense.
- Both `GET` and `POST` are behind `@login_required`, and the decorator keeps its
  `@wraps` so the `add_expense` endpoint name still resolves for `url_for`.
- No inline styles. `static/js/main.js` stays empty — a native `<select>`,
  `<input type="number">`, `<input type="date">`, and a plain POST are the whole
  interaction. No client-side validation standing in for the server checks.
- Amounts display in ₹ through the existing `_rupees()` helper; the stored row
  stays a raw `REAL`.
- Leave `/expenses/<int:id>/edit` and `/expenses/<int:id>/delete` as
  placeholders. This step is create only.

- [ ] Signed in as `demo@spendly.com` / `demo123`, `/profile` shows an
      "Add expense" button that links to `/expenses/add`.
- [ ] `GET /expenses/add` renders the form inside the site chrome (navbar +
      footer), with the seven categories in the dropdown and the date field
      pre-filled with today.
- [ ] Submitting amount `250.75`, category `Food`, today's date, description
      `Chai and samosas` redirects to `/profile`, where the row appears at the
      top of the transaction list as `₹250.75` with a Food badge.
- [ ] After that submit, "Transactions" reads 9 and "Total spent" has increased
      by exactly ₹250.75 (₹4,546.00 for an otherwise untouched seed database).
- [ ] The Food row in the category breakdown has grown by ₹250.75, and the
      breakdown totals still sum to the "Total spent" stat.
- [ ] Submitting with the description left blank succeeds, and the new row shows
      "—" in the Description column.
- [ ] Submitting a blank amount shows an error on the same page; the category,
      date, and description the user picked are still filled in.
- [ ] Submitting `abc`, `0`, and `-50` as the amount each show a specific error
      message and insert nothing — the profile transaction count is unchanged.
- [ ] `curl -X POST` (with a valid session cookie) sending
      `category=Cryptocurrency` is rejected with an error and inserts nothing.
- [ ] `curl -X POST` sending `user_id=<other user's id>` alongside valid fields
      creates the expense on the *signed-in* account, not the named one.
- [ ] Submitting `date=2026-02-31` or `date=banana` shows an error, not a
      traceback, and inserts nothing.
- [ ] Submitting tomorrow's date shows the future-date error and inserts nothing.
- [ ] A date inside an active profile filter range shows up when that filter is
      applied; a date outside it does not — confirming the stored value is ISO
      and Step 6's range query still works over it.
- [ ] A brand-new registered user sees the "No expenses yet" empty state with a
      link to add one, adds an expense, and sees exactly that one row — none of
      the demo user's eight.
- [ ] Refreshing `/profile` after a successful submit does not create a second
      copy of the expense.
- [ ] `sqlite3 expense_tracker.db "SELECT description FROM expenses WHERE
      description IS NULL"` returns the blank-description row — stored as NULL,
      not an empty string.
- [ ] The new page has no inline `style=` attributes, no new hex colours in
      `style.css`, and `static/js/main.js` is still behaviour-free.
